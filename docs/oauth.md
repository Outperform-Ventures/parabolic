# OAuth applications

Register an internal application in API settings or with `POST /api/v1/apps`. Registration stores exact redirect URIs and the maximum permitted scopes. The client secret is shown once; lists omit it. Redirect URIs must use HTTPS or loopback HTTP, without fragments or embedded credentials. Provider connectors remain deferred; OAuth supports your own tools today.

Navigate a browser to `/oauth/authorize?response_type=code&client_id=…&redirect_uri=…&state=…&scope=issues:read`. Supply `code_challenge` and `code_challenge_method=S256` for PKCE. The browser shows the account, current workspace, application name, requested access, and callback host. An unauthenticated user signs in and returns to this exact request. GET never grants access. Authorize and Deny are explicit user actions. Preregistered applications must belong to the active workspace. Dynamically registered MCP clients receive access only to the workspace selected during explicit consent.

For API clients, `GET /oauth/authorize` with `Accept: application/json` returns validated consent metadata and requires a browser session. `POST /oauth/authorize` with JSON `approve:true` creates a single-use code valid for five minutes. `approve:false` returns the registered callback with `error=access_denied`. Both outcomes preserve state. Unknown clients, mismatched redirect URIs, unsupported response types, or invalid scopes produce errors without redirecting to an untrusted address. The HTML response disallows framing through CSP.

`POST /oauth/token` accepts JSON or form encoding. Exchange with `grant_type=authorization_code`, `client_id`, `redirect_uri`, `code`, and either a confidential application's `client_secret` or the matching `code_verifier`. HTTP Basic client authentication is supported. A supplied secret is checked even when PKCE is present. The response contains `access_token`, `token_type`, `expires_in`, `refresh_token`, `refresh_token_expires_in`, and `scope`. Token endpoint failures use OAuth `error` and `error_description` fields.

Refresh with `grant_type=refresh_token`, `client_id`, `refresh_token`, and a client secret if the grant was created using confidential client authentication. An optional scope may narrow the grant. Access tokens last one hour. Refresh tokens expire after thirty idle days and no later than ninety days after the initial grant. Only token hashes are stored. Every refresh invalidates its predecessor and the previous access token. A replay of a consumed refresh token revokes every token in that grant. This follows the rotation and reuse-detection approach in [OAuth security best practice, section 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

`POST /oauth/revoke` accepts `client_id`, `token`, optional `token_type_hint`, and the applicable `client_secret`. Revoking either a refresh token or its access token revokes the full grant. Authenticated requests for unknown tokens succeed without revealing token existence, following [OAuth token revocation](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.2). Personal API key revocation, removed membership, and application changes also prevent a revoked grant from minting fresh credentials. Rotation is serialized in a SQLite transaction; clients must also serialize refreshes and atomically replace their stored token pair.

The MCP resource at `/mcp` supports protected-resource discovery, authorization-server metadata, and public client registration at `/oauth/register`. MCP grants require S256 PKCE and the exact MCP `resource` on authorization, code exchange, and refresh. Audience-bound tokens are accepted only by that MCP resource; they cannot access ordinary REST endpoints. See [MCP configuration](mcp.md). OpenID Connect identity tokens, Client ID Metadata Documents, implicit grants, and device flow are not advertised.

## Application identities and client credentials

An administrator can enable `clientCredentialsEnabled` when creating or updating an application. This permits registration without redirect URIs for an unattended internal service. Applications have `allPublicTeams` (default true) and `teamIds` access settings; public access excludes private or restricted ancestors. Selected teams must be accessible to the administrator configuring the application. Settings provides the same controls and a secret rotation action.

`POST /oauth/token` with `grant_type=client_credentials`, `client_id`, `client_secret`, and explicit `scope` returns a bearer token valid for thirty days. It has no refresh token. Up to 1,000 unexpired tokens with the same scopes can coexist. Requesting a different set of scopes revokes previous application-identity credentials; individual-user grants remain separate. Disabling client credentials revokes that grant type. Removing team access revokes application credentials, and rotating the secret at `POST /api/v1/apps/:id/rotate-secret` revokes all access, refresh, and pending code grants. The new secret is returned once.

Add `actor=app` to the browser authorization URL to install with an application identity. This requires administrator consent and confidential client authentication at code exchange, including when PKCE is present. App installations use normal code/refresh rotation afterward. Actions are attributed to a dedicated workspace member marked `isApp`; it has no login account and cannot acquire administrator or API-key management privileges. Team permissions are checked for direct records, lists/counts, GraphQL, search, streams, attachments, and collaborative rooms. Ordinary `actor=user` grants continue to use the consenting person's identity. Public dynamically registered MCP clients authorize users and cannot request application-identity or client-credentials grants.

The retained behavior follows Parabolic's [application actor authorization](https://parabolic.app/developers/oauth-actor-authorization) and [client credentials documentation](https://parabolic.app/developers/oauth-2-0-authentication). These are API service identities; they do not enable hosted AI sessions or provider connectors.
